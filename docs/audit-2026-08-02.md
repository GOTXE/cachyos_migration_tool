# Auditoría inicial — 2026-08-02

Estado: primera tanda de correcciones aplicada; queda pendiente probar el flujo real en el MBP.

## Correcciones aplicadas en esta tanda

- La TUI Bash y la TUI Python ya muestran operación fallida y código de salida cuando el proceso hijo termina con error.
- El stack Node comprueba al terminar que `node` y `npm` existen.
- La configuración de PATH para Fish incluye `~/.local/bin`, `~/.bun/bin` y las versiones NVM.
- El workaround Broadcom intenta añadir `brcmfmac.feature_disable=0x82000` a las líneas `cmdline:` de `/boot/limine.conf`, creando antes una copia `.bak.<timestamp>`.
- Sintaxis Bash, ShellCheck, compilación Python y tests existentes pasan.
- Las operaciones de bootstrap, backup y restore validan sudo una vez al inicio y mantienen viva la autorización durante la operación.
- Se añadió el bloque opcional `ai_antigravity`, que instala CLI `agy`, SDK Python en un entorno virtual y los dos tarballs de Antigravity proporcionados.

## Hallazgos confirmados

### Bootstrap y selección TUI

- El catálogo de bloques se define en `src/lib/common.sh:get_bootstrap_checklist_items` y los bloques de IA (`ai_codex`, `ai_claude`, `ai_gemini`, `ai_opencode`, `ai_engram`) aparecen desactivados por defecto.
- El ejecutor whiptail de `src/lib/tui.sh:tui_bootstrap_run` sí contiene ramas para Node, Codex y Claude.
- La instalación real registrada el 2026-08-02 no contiene llamadas a `install_node_stack`, `npm install -g @openai/codex` ni al instalador de Claude, pese a que el post-check confirma que Codex y Claude faltan. Hay que reproducir y trazar la selección completa del backend TUI utilizado.
- El catálogo de la máquina auditada numera 30=Hyprland, 33=MBP Watch y 34=Plasmoid MBP Watch. Excluir esos tres no debería excluir Node ni las CLIs de IA.
- Antigravity no tiene instalación inicial: solo existe una reparación post-restore de `google-auth-library` si ya existe un bundle en `~/.local/share/antigravity-ide/resources/app`.
- `src/lib/tui.py:run_op` no comprueba el código de salida de `subprocess.run`; puede presentar una operación fallida como completada.

### Node/npm y CLIs

- npm se instala indirectamente como parte del bloque Node/NVM; si ese bloque no se ejecuta, Codex/Gemini/pnpm tampoco pueden instalarse.
- El bootstrap enlaza binarios npm a `~/.local/bin`, pero la verificación depende del PATH de la sesión actual y no valida de forma robusta que npm, Node y cada CLI terminen disponibles.

### Wi-Fi y Limine

- El workaround Broadcom crea `/etc/modprobe.d/brcmfmac-apple-bcm43602.conf` con `feature_disable=0x82000` y recarga el módulo.
- No se añade ese parámetro a `KERNEL_CMDLINE` ni se actualiza `limine.conf`; en el caso auditado fue necesario hacerlo manualmente.

### Tests y calidad operativa

- `tests/run.sh` no tiene bit ejecutable; `./tests/run.sh` devuelve `Permission denied`, aunque `bash tests/run.sh` pasa.
- Los tests actuales cubren principalmente perfiles y texto del catálogo; no cubren el contrato TUI Python → `tui-bootstrap-run`, errores de subprocesos, instalación Node/CLIs, restore de `.ssh`, ni actualización de Limine.

### Evidencia de red

- Los logs contienen errores de resolución/DNS y descargas fallidas de mirrors de CachyOS. El bootstrap no parece convertir estos fallos en un resumen final fiable ni en una verificación por bloque.

### Backup `.ssh`

- El backup contiene `configs/.ssh` con `id_github`, `config`, `known_hosts` y varias claves privadas. Todavía no se ha copiado al sistema actual.

## Incidente posterior: BCM43602 tras suspensión

En una segunda prueba real, el Wi-Fi volvió a perder el escaneo. El análisis del
boot anterior confirmó que no era un problema de DNS ni de NetworkManager:

- `brcm_pcie_pm_enter_D3 returns -5` al intentar suspender.
- La suspensión falló y el firmware quedó en un estado inconsistente.
- Después aparecieron `Failed to reserve space in commonring`, `scan error (-12)`
  y timeouts `-5` del driver `brcmfmac`.
- El reinicio completo recuperó la interfaz.

Se añadió un hook `systemd-sleep` para descargar el módulo antes de suspender y
recargarlo después. El bootstrap también instala este hook para futuras máquinas
con BCM43602 Apple. Falta validar una suspensión real con el hook activo; si aún
falla, las alternativas son desactivar suspensión en este modelo o probar otro
kernel/firmware. El sistema sigue reportando ausentes `clm_blob` y `txcap_blob`.
